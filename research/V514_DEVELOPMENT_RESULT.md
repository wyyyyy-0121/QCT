# V5.1.4-development：候选扩展、消融与新实例确认

## 结论

本轮按顺序完成了未修复原因分解、接受前候选覆盖率评估、受约束的边缘候选
扩展、开发消融、源码/协议冻结和新实例确认。定位器没有重写，全部定位不变量通过。

**候选能力有所补充，但实验性自动接受未通过安全门槛，结论为 DO_NOT_PROMOTE。**
默认模式仅增加边缘复核提案，保留旧 V5.1.2 接受机制；不能称为更强的自动修复模型。
两方向一致的实验接受仍保留在显式 `edge_mode="orthogonal"` 中，供复现实验。

## 1. 先交付的未修复原因分解

详见 `V514_CANDIDATE_AUDIT.md`。在 144 个已揭盲夹具中，268 个应修复错误格：

- 已正确修复 60 格。
- 结构机制没有正确候选：12 格，全部为边缘单点。
- 正确候选存在、授权证据不足：196 格，全部为多数受损区域。
- 证据通过但被规则异常阻断：0 个已证实案例。

未修复三类合计 208。分类以原 V5.1.2 结构机制为对象；不是说 V4 也没有这些建议。
原始结构候选覆盖 256/268（95.52%）；与 V4 提案的 oracle 并集覆盖 268/268。
正确候选存在不等于具备充分接受证据；原子组和分差条件不能被单格 passes 替代。

本轮独立核对了实际 V5.1.3 精选候选档案：在旧夹具上，V4 组合已经覆盖
268/268，V5.1.1 组合为 256/268。因此不能宣称扩展提高了 V4 组合的候选覆盖率。

## 2. 边缘扩展实现与适用范围

实现文件：`formulaguard/v5_1_4_development.py`；API 新增 `v5.1.4-development`。

1. 只在连续公式区域的单格端点生成提案；相邻健康模板至少有 3 个连续支持格。
2. 所有锚点翻译到目标格后必须一致，保存每个锚点坐标、方向和候选公式。
3. 单侧证据只产生复核提案；不修改定位分数，也不授权整块/整列修复。
4. 实验性接受要求行、列两个不重叠锚点集合支持同一公式，且为一次受限结构编辑。
5. 字面常量变化、删除折扣因子、表达式结构变化仍为复核；冲突候选不得接受。
6. 继承 V5.1.3 的完整定位、候选档案、独立接受三层接口；旧原子接受组保留。

两个锚点集合不重叠，仅说明不是同一单元格重复投票；**不证明业务含义独立**。
合法边缘例外可以与错误具有相同结构，这正是实验性接受失败的原因。

```python
from formulaguard.v5_1_4_development import diagnose_v5_1_4_development

d = diagnose_v5_1_4_development(model, localization_backend="v4")
assert d.edge_mode == "propose_only"  # 默认：新增边缘提案只交给复核
ranking = d.localization
proposals = d.candidates
decisions = d.decisions

# 仅用于复现实验；本轮确认其安全性未通过，不是推荐的自动修复策略。
experimental = diagnose_v5_1_4_development(model, edge_mode="orthogonal")
```

没有自动写回工作簿，没有更改生产默认模型，没有上传 GitHub。

## 3. 开发消融与整段/整列诊断

每个数据集均测试 2 个定位后端 × 3 个候选/接受模式 × 3 个修复策略，共 18 个组合。
模式为 off、propose_only、orthogonal；策略为 structural、review_only、reject_all。
off 是 V5.1.3 组合基线。propose_only 不禁用旧结构接受，只禁止新增边缘自动接受。

### 旧的 144 个夹具

| 定位后端 | 模式 | 候选覆盖 | 正确接受覆盖 | 不安全接受组 |
| --- | --- | ---: | ---: | ---: |
| V4 | off | 268/268 | 60/268 | 0 |
| V4 | propose_only / orthogonal | 268/268 | 60/268 | 0 |
| V5.1.1 | off | 256/268 | 60/268 | 0 |
| V5.1.1 | propose_only / orthogonal | 268/268 | 60/268 | 0 |

新增提案补齐了 V5.1.1 组合的 12 个边缘正确候选，但这些旧案例没有另一方向的
可信参照，接受数没有增加。该结果是候选补充，不是安全修复覆盖提升。

196 个多数受损区域的正确提案已存在，但缺少足够授权证据，继续保留复核。
新生成数据另含多数受损区域、整列无健康锚点、短区域和方向冲突四类压力案例。
确认集这些类别合计 96 个工作簿，均没有被实验模式接受。没有用降低门槛把
这类证据不足的问题包装成整列修复能力；后续需要外部约束、可靠跨区域关系或
人工明确的业务规则。当前研究不能证明哪一种额外约束必然充分。

### 132 个新开发网格

6 个公式家族 × 2 个模板簇 × 11 类案例。开发集已观察到：
实验模式正确修复 24/36 个应修复错误格；36 个接受组中有 12 个合法例外误修，
组精度 66.67%，控制误报率 12/48 = 25%。因此在冻结前将默认模式设为 propose_only。
此改变只影响默认选项；orthogonal 实验规则未为改善结果而删改反例或降低标准。

### 25 个真实工作簿

使用已校验的共同运行环境 V4/V5.1.1 定位缓存，重新运行修复与组合。
两个后端的三个模式都输出原有的 11 个接受候选，新增边缘接受数为 0。
真实表修复真值不完整，不计算修复精度或误报率，不把 11 个候选称为正确修复。
完整定位排名与 V5.1.3 对应后端相同，输入层原有缺失标签未被本轮“修复”。

  48.38 秒；Ruff 全仓通过。
- 144 旧夹具 + 25 真实表 + 132 开发网格 + 264 确认网格 = 565 个工作簿实例。
- 30,670 个公式格 × 18 组合 = 552,060 个单元格/组合检查。
- 排名变化 0，分数位模式变化 0，公式格遗漏/新增 0；每个组合均双算并检查一致。
- 共 10,170 个预测分片逐个非空、哈希一致。401 份冻结源码及源码副本在评分后仍匹配。
- 评分协议测试包括分片篡改、重算哈希后的排名篡改、覆盖缺失和变体缺失；
  必须在写揭盲授权之前拒绝。不只相信汇总文件声明的零变化。
- 独立从确认标签及原始动作重新汇总：应修复 72、正确动作 48、控制 96、
  控制误报 24、接受组 72、不安全组 24，与正式评分一致。

分析验证结论：**Share with caveats**。候选与接受分开计数，控制与应弃权分母分开，
未因反例导致安全失败而删例。全部 24 个合法例外误修已经构成反证，不需要
通过显著性检验才能否定“无不安全接受”。

仅作独立二项近似的描述性区间：控制误报率 25% 的 Wilson 95% 区间约
17.41%–34.51%；接受组精度 66.67% 的区间约 55.18%–76.47%。应弃权案例
0/96 接受的一侧 95% 上界约 3.07%。实际存在模板簇相关性，这些区间不能
作为总体泛化置信保证；尤其不能据 0/96 声称真实风险为零。

- 生成器：`scripts/build_v514_edge_cases.py`，不导入模型推理代码。
- 运行/评分入口：`scripts/evaluate_v514_edges.py`，拒绝覆盖输出目录。

复现当前确认结果可先用冻结锁验证现有输入/预测，再在新输出目录重评分：

```bash
.venv/bin/python scripts/evaluate_v514_edges.py score \
  --source-lock results/v514_edge_freeze_v1/source_lock.json \
  --release results/v514_edge_confirmation_release_v1 \
  --predictions results/v514_edge_confirmation_predictions_v1 \
  --output results/v514_edge_confirmation_rescore
.venv/bin/python -m pytest -o addopts= -q
.venv/bin/ruff check .
```

重新运行 build 会使用新种子，属于新一批实例，不是原确认数据的逐字节复现。
SHA-256 可以发现更改，但不能保证有系统写权限的人绝对无法修改文件。
历史模型、结果和锁文件保留；共用 API 调度文件只新增开发入口。

## 下一项研究应解决什么

默认候选扩展可以保留供复核；不要开启本轮失败的 orthogonal 自动接受作为升级。
下一步不是继续调结构阈值，而是明确哪些业务约束可被信任，例如用户确认的
总额关系、经验证的同义区域对应或显式例外标注，并验证这些约束是否能区分
当前不可识别的合法例外。没有新授权证据时继续弃权，而不是追求整列自动修复。
