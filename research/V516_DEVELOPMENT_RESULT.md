# V5.1.6-development：多错误联合修复与约束歧义处理

## 结论

四项交付均完成：联合候选判断、完整搜索下的唯一性判断、正反例生成、与
V5.1.5 的同场消融及冻结后确认。确认结论为
`PASS_CONDITIONAL_SYNTHETIC_EXPERIMENT`，不代表真实业务安全性或生产晋升。

在同一批 360 个确认案例的 570 个应修复错误格中，V5.1.5 正确修复 30 个，
V5.1.6 正确修复 240 个：覆盖率 **5.26% → 42.11%**，增加 210 个正确修复格。
两个后端结论一致，均没有观察到不安全接受组。完整定位与候选生成未修改。

## 1. 实现：从逐格修复到联合事务

新模块 `formulaguard/v5_1_6_development.py`，API 方法 `v5.1.6-development`。
复用 V5.1.5 的文档批准、内容绑定、有效期、求值和完整性检查，复用 V5.1.4
受限边缘候选，不重新训练或重排定位器。

每个直接参与 aggregate 的候选单元格都有“不改”和不同候选公式选项。
系统计算全部选项的笛卡尔积大小，默认上限 256。只在完整检查全部状态且恰有
一个满足所有约束的状态时接受；不按更少修改数擅自打破多解平局。

| 搜索结果 | 决策 |
| --- | --- |
| 完整搜索且恰有一个解 | 实验性整组接受 |
| 多个解 | 复核并报告歧义 |
| 无解 | 不接受，报告无解 |
| 超预算或某个状态无法完成求值 | 不接受，不声称唯一 |
| 原式满足全部约束 | 不修改，包括仅总额无法识别的错误抵消 |

候选空间的“唯一”只覆盖直接约束成员上的现有受限边缘提案，并非任意上游
公式、所有可能公式或业务解释的唯一性。在有效约束路径内，不把旧接受动作
偷偷合并到新事务；输出完整验证的唯一修改组。无批准约束时保留既有回退行为，
但不称其为联合约束授权。

`JointDiagnosis.search` 记录状态、空间大小、已枚举数、解数、完成标志和候选格数。
拒绝、复核以及改变预算均不改变 `localization`，候选档案仍可检查。

```python
from datetime import date
from formulaguard.v5_1_6_development import (
    SearchParameters, diagnose_v5_1_6_development,
)

d = diagnose_v5_1_6_development(
    model, documents=[document_bytes], approvals=approved_hashes,
    as_of=date(2026, 9, 6), config=SearchParameters(max_states=256),
)
print(d.search.status, d.search.complete, d.search.evaluated)
ranking, candidates, decisions = d.localization, d.candidates, d.decisions
```

## 2. 生成的正例与反例

开发 144 个案例，确认 360 个案例；六类算术模板、十二类情形，开发每家族
两个簇、确认每家族五个新簇。总额覆盖全部固定区域，部门小计覆盖整个部门，
不是为每个被损坏的单元格单独生成答案方程。文档不含目标公式。

- single：单错误，保留已有能力。
- joint_two / joint_three：只有联合修两格或三格才能恢复总额。
- ambiguous：两个不同单格方案都满足总额，不能区分错误与合法端点例外。
- cancel_total：两项错误相互抵消，只看总额不应修改。
- cancel_subtotals：同样存在抵消，但固定部门小计提供额外判别信息。
- legal_exception / clean：合法例外和干净控制。
- expired / conflict：过期或矛盾约束。
- numeric_collision：错误公式在当前数值上碰巧相等，不应声称已辨认。
- budget：九个二选一候选，512 个状态，超过默认 256 上限。

预算案例不是不可能修复，而是本轮未完整搜索，因此必须保留在分母里并拒绝
自动接受。无法求值导致搜索不完整的分支由注入式回归测试验证，未冒充为确认集
中的一个独立自然案例。

合成外部账本的真实性是声明前提。新种子改变实例，但使用相同已知生成器家族；
这不是第三方盲测或真实工作簿泛化验证。工作簿、文档和批准上下文共同构成案例，
模板和部分内容重复是设计的一部分，不能把所有实例当作独立自然样本。

## 3. 同场比较和消融

每个案例采用 V4/V5.1.1 两个定位后端，分别运行 V5.1.5、V5.1.6、低预算 1、
仅复核和全部拒绝，共十个组合。两个后端各自的定位排名不变，不跨后端混比分数。

开发结果：V5.1.5 12/228 正确修复，V5.1.6 96/228；接受组分别 12/12、48/48
全部正确。先完成开发评分与测试，再冻结和生成确认集。

### 冻结后确认：全部人群

360 案例包括 210 个应修复案例（570 个错误格）、60 个控制、90 个应弃权案例。
候选正确答案覆盖均为 570/570；提升来自联合接受能力，不是新增答案来源。

| 模式（两种定位后端结果一致） | 正确修复覆盖 | 接受组全对率 | 不安全组 |
| --- | ---: | ---: | ---: |
| V5.1.5 | 30/570，5.26% | 30/30 | 0 |
| V5.1.6 联合搜索 | 240/570，42.11% | 120/120 | 0 |
| V5.1.6 预算上限 1 | 0/570 | 不适用 | 0 |
| 仅复核 / 全部拒绝 | 0/570 | 不适用 | 0 |

没有通过低预算零动作宣称更强安全修复能力。主结果的覆盖提升为 36.84 个百分点，
新增 210 个正确修复格、90 个正确接受组。

### 提升来自哪里

| 情形 | 确认案例 | 错误格 | V5.1.5 正确修复 | V5.1.6 正确修复 |
| --- | ---: | ---: | ---: | ---: |
| 单错误 | 30 | 30 | 30 | 30 |
| 必须联合修两格 | 30 | 60 | 0 | 60 |
| 必须联合修三格 | 30 | 90 | 0 | 90 |
| 用部门小计识别抵消 | 30 | 60 | 0 | 60 |
| 超预算九错误 | 30 | 270 | 0 | 0 |
| 过期约束 | 30 | 30 | 0 | 0 |
| 数值碰巧相等 | 30 | 30 | 0 | 0 |

剩余 330/570 格未修复，其中 270 格来自超预算案例。多解、只有总额的错误抵消、
矛盾约束属于单独的 90 个应弃权案例；它们的任何接受均计不安全，结果为零。
60 个控制案例也没有接受。全体案例的无接受动作比例为 240/360（66.67%），
其中包括合法/干净案例，不能把这个比例全部解释成模型失败。

## 4. 唯一性与搜索成本

主联合模式每个后端的状态分布：唯一解 120；原约束已满足 120；多解 30；
无解 30；超预算 30；过期约束 30。全部 120 个接受组都验证了 complete=true、
evaluated=space_size、solutions_seen=1，并逐成员核对正确公式和完整组大小。

每个后端主联合模式枚举计数合计 840，最大声明空间 512；512 状态的案例均
预检拒绝，枚举计数为零。计数不包括准备求值、双跑重复和预算预检前的原约束
检查；原式已经满足而提前返回时记一个原状态。

冻结后另做工程边界检查：8 个候选共 256 个状态，完整枚举后唯一接受 8 格；
把预算改为 255 时拒绝，定位不变。这个额外测试没有加入确认集成绩，也没有
改动冻结源码。完整搜索仍有组合爆炸风险，不能据小样本运行时间宣称可扩展。

V4 后端 360 次诊断耗时之和：V5.1.5 约 2.595 秒，联合版约 2.237 秒；
单次最大约 44.7 毫秒和 32.0 毫秒。这是 24-worker 环境下每次诊断的墙钟计时
之和，不含定位、磁盘写入和二次一致性检查，不是隔离 CPU 或生产延迟基准。
联合版能提前拒绝大空间，因此不能用这个差异声称搜索复杂度更低。
