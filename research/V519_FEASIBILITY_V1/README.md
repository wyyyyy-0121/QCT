## 2. 两类瓶颈

依赖案例的准备求值、剪枝数和已发现解数均为零，4096 个叶求值后停止。
开发规模 16/24/32 格，原确认规模 24/32 格；空间为 `2**16` 至 `2**32`。
访问节点为 8208/8216/8224，未达到 10000；提高节点预算不会解除当前瓶颈。
原确认保存的诊断证书序列化大小为 426700–525006 字节，虽然并未证明唯一性。

弱界限案例已启用 binary64 剪枝，但到 10000 节点时仍未抵达任何完整叶赋值，
已发现解数为零。准备求值为 34/50/66；原确认剪枝仅覆盖 12912–12920 个状态。
单候选之间不存在检测到的依赖，提高叶求值预算或只做依赖分组均不解决该瓶颈。
其目标总额由生成器作三分之一差额偏移，标签要求拒绝；当前超预算记录没有
证明全空间无解，不能将其自动记作 `no_solution`，更不能把它当作待接受修复。

## 3. 依赖证据的局限

生成器在 `Dept_001` 首行 B 格引入 `原常数 + 0 * Dept_000!H...`。
引用图存在跨候选依赖，但在这些有限、无求值错误的输入上，另一候选不改变
本候选数值。对全部 15 个依赖工作簿的两候选四种组合实际求值，共 60 个
局部赋值，观察到的跨候选数值变化均为零。这不是删除一般 `0*x` 引用的证明：
循环、缺失、未知和非有限值仍可能影响求值行为。

按原/候选引用并集及每个 aggregate 成员的候选支持集合构建无向组件：
每个依赖案例只有一个大小为 2 的组件，其余均为单候选。局部表行数估算
`4 + 2*(n-2) = 2*n`，即 32/48/64；全局空间仍分别为 `2**16/24/32`。
这是组内枚举规模估算，不是求解耗时、准备求值次数或唯一性结论。
弱界限案例全部为单候选组件，同样有 2*n 表行，不存在分组带来的结构改善。

## 4. 对 V519 的影响

建议实验主线为真实数值依赖的组件枚举与全局保守剪枝。先用小空间完整穷举
验证，再进入较大规模。旧零系数案例只作为回归，不能单独支撑“支持依赖修复”。
弱界限列为必测压力项；若要优化离散可达总额，必须单独提出含浮点容差和
完整空间覆盖的证明，不能把它混作依赖分组的收益。

即使未来全部修复原确认的 12 个依赖案例，也只是最多新增 336 个正确格，
得到 `(672+336)/2724 = 37.00%` 的条件性算术情景。尚未实现或验证，既不是
预测结果，也不能把剩余多解、抵消、批准无效或无解案例都视为算法应修复的格。
