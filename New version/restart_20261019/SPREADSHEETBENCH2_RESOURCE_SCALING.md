# SpreadsheetBench 2 并发扩展资源实验

记录时间：2026-10-19。该实验是在原1/4/8-worker资源试跑和100项8-worker基线启动后追加的探索性运行设置，不属于事前登记，不改变冻结基线或其准确率评估。

## 目的与边界

本机当前通过WSL可见32个逻辑CPU（16个物理核心）和约15.2GiB内存。现有主基线使用8个worker并已锁定；后续批量实验固定请求20个worker。并发扩展只回答更高工作簿并发对墙钟时间、CPU利用和内存的影响；不读取或改用golden、任务标签，不调整模型、阈值、单项900秒上限或评分定义。

现有1/4/8-worker试跑均为9项完成、1项900秒超时，墙钟分别为922.61、904.35和900.63秒。由于超时截断主导了总时长，这些数值不能支持可靠的加速比结论。试跑的采样峰值聚合RSS为607–670MiB；100项基线仍在运行时，两个长任务各自RSS约415MiB。故试跑内存不能代表全量运行峰值。

运行器每个worker按1GiB进行内存准入估算，使用当时可用内存的70%作为准入预算。按本轮观察的可用内存，这会把16或20的请求压到约9个有效worker。扩展实验改用550MiB/worker作为准入估值；按当前约13.1GiB可用内存，70%预算约9.2GiB，可容纳16×550MiB。该估值略高于当前两个长任务各约415MiB的实测RSS，但不是操作系统硬上限。只有运行器记录的有效worker数为16且启动预算至少覆盖16×550MiB时，才认为16-worker运行成立；否则不开始或不把它报告为16-worker结果。

## 执行顺序

1. 等待100项8-worker基线完成并生成预测锁。先验证锁覆盖100项终态、原模型/脚本/输入哈希一致，以及每个成功预测文件哈希正确。
2. 再次验证100项输入哈希及冻结模型树哈希。使用同一`full_workers_8.jsonl`作为16-worker清单，在新目录`runs/full_workers_16/`运行；原目录和预测锁均不覆盖。
3. 仍按每项900秒截止，记录逐项终态、有效worker数、整批墙钟时间、子进程CPU时间和采样聚合峰值RSS。若有任务缺少终态、输入改变、运行器实际worker数不是16，或RSS采样显示环境资源异常，则停止扩展解释并保留日志。
4. 对照8-worker锁逐项比较状态、返回码和成功预测SHA-256。差异必须报告并调查，不能将不同执行结果合并或挑选有利结果。两种并发下超时仍计入任务覆盖率分母。
5. 16-worker完整复跑已经完成并与8-worker逐项一致。按用户要求，20-worker复跑不再作为并发档位比较；一次复跑在90/100项完成时中止，部分目录和预检记录仅作执行痕迹，不用于速度或准确率结论。后续新批次默认请求20个worker，并遵守同样的内存准入。

## 解释限制

新增运行是对同一冻结模型和同一100项输入的重复推理，属于资源实验，不替代8-worker基线，也不增加独立准确率样本。加速比仅在逐任务结果可比、CPU计量完整且完整批次的墙钟结果未被不同超时截断支配时报告；否则报告原始耗时、有效并发、CPU和RSS，并说明不能形成可靠加速比。GPU未监测，不作GPU利用率结论。
